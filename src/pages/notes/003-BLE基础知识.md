## 1. 笔记简介

蓝牙是一类工作在 2.4 GHz 频段的短距离无线通信技术，常用于耳机、键盘、传感器、穿戴设备和智能家居等场景。实际开发中经常接触到两条技术路线：经典蓝牙（Bluetooth Classic，也叫 BR/EDR）和低功耗蓝牙（Bluetooth Low Energy，简称 BLE）。

BLE 的难点通常不在于某一个 API，而在于容易把几组不同层级的概念混在一起，例如 Central 与 Client、Peripheral 与 Server、Service 与 Characteristic。理解 GAP 负责什么、GATT 负责什么，以及数据究竟由谁发起传输，是继续学习 BLE 协议栈和应用开发的基础。

## 2. 核心知识点

### 2.1 经典蓝牙与BLE不是同一种空中传输

经典蓝牙和 BLE 都属于蓝牙技术，也都使用 2.4 GHz ISM 频段，但它们使用不同的无线传输方式和协议栈，不能把 BLE 当成“仅仅降低了功耗的经典蓝牙”。

| 对比项 | 经典蓝牙 BR/EDR | BLE |
|---|---|---|
| 典型数据形态 | 持续传输、连续数据流 | 少量数据、间歇传输、短数据包 |
| 典型用途 | 耳机、音箱、车载音频、传统串口透传 | 传感器、穿戴设备、遥控器、状态上报 |
| 无线信道 | 79 个 1 MHz 信道 | 40 个 2 MHz 信道，其中包含广播信道和数据信道 |
| 常见上层模型 | A2DP、HFP、SPP 等经典蓝牙 Profile | 以 ATT/GATT 属性数据模型为核心 |
| 通信拓扑 | 主要是点对点 | 点对点、广播、Mesh 等 |
| 设备发现 | Inquiry / Paging 等机制 | Advertising / Scanning |

二者的核心区别首先是**无线传输和协议体系不同**，其次才是由设计目标带来的功耗、数据模型、连接过程和应用场景差异。经典蓝牙偏向持续的数据流，BLE 偏向设备先广播、需要时快速连接、短时间交换少量数据，然后尽可能休眠。

这也意味着：

- 只支持经典蓝牙的设备不能直接连接只支持 BLE 的设备；
- 同时支持二者的芯片或适配器称为双模设备；
- BLE 并不天然等于“传输速度一定更慢”，实际吞吐量还取决于 PHY、连接间隔、MTU、数据长度和协议开销；
- 现代 BLE 已经支持 LE Audio，因此“经典蓝牙负责音频、BLE 绝不传音频”也不是绝对规则。

蓝牙 SIG 的[技术概览](https://www.bluetooth.com/learn-about-bluetooth/tech-overview/)给出了两种无线方式在信道、PHY、速率和拓扑上的正式对比。

### 2.2 BLE协议栈的基本层次

BLE 不是一个单独的通信协议，而是一套分层协议。初学阶段可以先建立下面这张简化结构：

```text
应用程序
   │
GAP：发现、广播、扫描、连接
GATT：服务和特征值的数据模型
ATT：属性的读取、写入和传输
L2CAP：上层数据适配与复用
   │
Link Layer：广播、连接、信道和时序
PHY：2.4 GHz 无线收发
```

此外，SMP（Security Manager Protocol）负责配对、密钥和加密等安全过程。实际协议栈的结构比这张图更完整，但先分清 GAP、GATT、ATT 和底层无线链路，已经能够解释大部分常见 BLE 应用。

BLE 的通信距离也不是固定的“几米到几十米”。实际距离会受到发射功率、接收灵敏度、天线设计、环境干扰、遮挡和所用 PHY 等因素影响。室内常见距离可能是几米到几十米，使用 LE Coded PHY 和合适硬件时还可能更远。

### 2.3 GAP负责发现与连接

GAP 是 Generic Access Profile，主要规定设备如何被发现、如何建立连接，以及连接前后的通用行为。BLE 中常见的 GAP 角色有四种：

| GAP 角色 | 主要行为 |
|---|---|
| Broadcaster | 发送不可连接广播，不建立连接 |
| Observer | 扫描和接收广播，不建立连接 |
| Peripheral | 发送可连接广播，接受 Central 发起的连接 |
| Central | 主动扫描，并向 Peripheral 发起连接 |

因此，把 Central 理解为“主动扫描并发起连接的一方”、把 Peripheral 理解为“广播并接受连接的一方”，在常见点对点 BLE 场景中是成立的。

不过，“Peripheral 只能等待别人连接”并不完整。Peripheral 在连接前会主动发送广播；连接建立后，双方都可以在协议允许的范围内发送数据。Central 与 Peripheral 描述的是**连接如何建立**，并不直接规定应用数据只能由谁发给谁。

### 2.4 GATT负责组织和访问数据

GATT 是 Generic Attribute Profile，它建立在 ATT 属性协议之上，用一棵层级结构组织应用数据：

```text
GATT Server
└── Service
    ├── Characteristic
    │   ├── Value
    │   └── Descriptor
    └── Characteristic
        ├── Value
        └── Descriptor
```

- **Service** 表示一组相关功能，例如心率服务或环境监测服务；
- **Characteristic** 表示一个具体数据项或操作入口；
- **Value** 是特征值真正保存的数据；
- **Descriptor** 用来补充描述特征值，其中常见的 CCCD 用于控制通知或指示。

Service、Characteristic 和 Descriptor 都通过 UUID 标识。蓝牙 SIG 已分配的标准项目经常使用 16 位 UUID；自定义服务更适合使用自行生成的 128 位 UUID，避免与标准编号或其他厂商发生冲突。

调试工具显示 `Unknown Service`，通常不代表服务无效，而是工具的名称数据库不认识这个自定义 UUID。它仍然可以显示 UUID、属性权限和原始数据。

### 2.5 `0x1800`与`0x2A00`的关系

`0x2A00` 不是一个服务 UUID，而是 **Device Name Characteristic** 的 UUID。它位于 UUID 为 `0x1800` 的 **Generic Access Service** 中。

```text
Generic Access Service：0x1800
└── Device Name Characteristic：0x2A00
    └── Value：设备名称
```

读取 `0x2A00`，本质上是在读取 Device Name 这个 Characteristic 的 Value。蓝牙 SIG 的[官方 Assigned Numbers](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Assigned_Numbers/out/en/Assigned_Numbers.pdf)记录了标准服务和特征值 UUID 的分配。

设备名称还可能出现在广播包或扫描响应包中。广播名称用于扫描阶段展示，`0x2A00` 则是连接后通过 GATT 访问的设备名称；两者通常设置成一致，但在协议上不是同一份数据。

### 2.6 GAP角色与GATT角色相互独立

GATT 不使用“主设备、从设备”这组角色，而使用：

| GATT 角色 | 作用 |
|---|---|
| Client | 发起服务发现，以及读、写、订阅等操作 |
| Server | 保存属性数据库，并响应访问或发送通知 |

最常见的组合是：

```text
一端：GAP Central + GATT Client
另一端：GAP Peripheral + GATT Server
```

但这只是常见组合，不是强制绑定。一个 Central 可以同时充当 GATT Server，一个 Peripheral 也可以充当 GATT Client；同一条连接的两端还可以同时拥有 Client 和 Server 功能。

因此不能说“Central 在 GATT 中不一定是 Service，它可能是 Client”。更准确的表达是：**Central 是 GAP 角色，Client 是 GATT 角色；Service 是 Server 属性数据库中的一组数据，不是设备角色。**

### 2.7 读、写、通知与指示

BLE 数据访问中的方向由 GATT Client 和 Server 决定，而不是由 GAP 的 Central 和 Peripheral 决定。

| 操作 | 发起方 | 数据方向 | 是否需要对端确认 |
|---|---|---|---|
| Read | Client | Server → Client | Server 返回读响应 |
| Write Request | Client | Client → Server | Server 返回写响应 |
| Write Command | Client | Client → Server | 不返回应用层写响应 |
| Notification | Server | Server → Client | 不对每条通知确认 |
| Indication | Server | Server → Client | Client 必须确认 |

Server 不能在任意时刻直接向 Client 发送 Notification。Client 一般需要先写入该特征值的 CCCD，启用通知，Server 才开始推送。这就是调试工具中“订阅通知”的实际含义。

## 3. 我的理解重述与修正

蓝牙是一套短距离无线通信技术，其中经典蓝牙和 BLE 是两套不同的无线传输与协议体系。经典蓝牙更适合持续的数据流，BLE 更适合广播发现、短连接和少量状态数据交换，低功耗只是这些设计差异带来的重要结果之一。

在常见 BLE 点对点通信中，GAP 负责设备发现和连接建立。Central 扫描并发起连接，Peripheral 发送可连接广播并接受连接。连接建立后，GATT 再负责组织和访问业务数据。

GATT Server 通过 Service、Characteristic 和 Descriptor 构成属性数据库。Service 是一组相关功能，Characteristic 是具体的数据项或操作入口，每一项通过 UUID 标识。标准 UUID 可以被调试工具翻译成名称，自定义 UUID 通常只显示原始编号或 `Unknown Service`，但不影响通信。

GAP 的 Central / Peripheral 与 GATT 的 Client / Server 是两组独立角色。`Central + Client` 和 `Peripheral + Server` 是最常见的组合，但协议并不要求永远这样对应。读和写由 Client 发起，通知和指示由 Server 发起；它们不能简单表述为“主设备读写、从设备通知”。

## 4. 疑问与解答

### Q1：除了低功耗，经典蓝牙和BLE最关键的区别是什么？

直观地说，经典蓝牙更像一条建立后持续传输的数据通道，BLE 更像一个围绕“广播、发现、连接、访问属性”设计的轻量数据系统。

从技术上说，二者使用不同的 Link Layer、信道组织、设备发现过程和上层协议模型。经典蓝牙常通过 A2DP、HFP、SPP 等 Profile 完成功能；BLE 常通过 ATT/GATT 暴露结构化数据。它们不是同一种协议的两个功耗档位，也不能由只支持其中一种的设备直接互通。

对于传感器值、按键状态等少量数据，BLE 的广播与 GATT 模型通常更自然。对于传统高质量音频或现成的串口 Profile，经典蓝牙的成熟 Profile 更直接，但现代 LE Audio 和厂商自定义 BLE 数据通道让边界不再绝对。

### Q2：Peripheral是不是只能等待别人连接？

不是。Peripheral 会主动、周期性地发送广播，只是普通连接通常由 Central 发起。

连接建立后，Central 和 Peripheral 都参与双向通信。谁读取、谁写入、谁发送通知，要看双方的 GATT Client / Server 角色和 Characteristic 属性，而不是只看 GAP 角色。

### Q3：Central一定是Client，Peripheral一定是Server吗？

不一定。这只是最常见、也最容易理解的组合。

Central / Peripheral 属于 GAP，描述设备发现和连接建立；Client / Server 属于 GATT，描述属性数据由谁发起访问、由谁保存。两组角色处于不同层次，可以自由组合。

### Q4：自定义服务为什么显示为Unknown Service？

调试工具通常内置了蓝牙 SIG 标准 UUID 与名称的对应表。标准服务可以显示 Heart Rate Service 等名称，而自定义 UUID 不在这张公共表中，所以工具可能显示 `Unknown Service`。

这只是“没有可显示的标准名称”，并不代表服务注册失败。判断服务是否正常，应检查 UUID、Characteristic、Properties、权限以及实际读写结果。

### Q5：一个Service应该包含几个Characteristic？

协议没有固定数量，应该根据业务数据之间的关系来设计。

相互独立、访问方式不同的数据适合拆成多个 Characteristic；需要同时更新、始终作为一个整体的数据，也可以编码在同一个 Characteristic 中。设计时需要综合考虑可读性、数据一致性、传输次数和后续扩展。

### Q6：Read、Write和Notification分别适合什么场景？

- Read 适合 Client 偶尔查询当前值；
- Write 适合 Client 向 Server 发送配置、命令或数据；
- Notification 适合 Server 在数据变化时主动推送；
- Indication 适合必须确认已经送达的重要数据。

如果数据经常变化，让 Client 高频轮询 Read 会产生不必要的通信。此时订阅 Notification 通常更自然。如果每条数据都必须得到协议层确认，则可以考虑 Indication。

## 5. 易混淆点对照

| 易混淆点 | 正确理解 |
|---|---|
| 经典蓝牙与BLE | 是两套不同的无线传输和协议体系，不只是功耗高低不同 |
| Central与Peripheral | GAP 角色，描述扫描、广播和连接建立方式 |
| Client与Server | GATT 角色，描述谁发起数据访问、谁保存属性数据库 |
| Service与Server | Service 是一组属性；Server 是承载这些属性的设备角色 |
| Central与Client | 常一起出现，但不是强制绑定 |
| Read与“主设备读” | Read 由 GATT Client 发起，与 GAP Central 身份没有必然关系 |
| Notification与广播 | Notification 发生在连接内，广播发生在广播信道上，不需要先建立普通连接 |
| Notification与Indication | Notification 不逐条确认；Indication 需要 Client 确认 |
| `0x1800`与`0x2A00` | `0x1800` 是 Generic Access Service，`0x2A00` 是 Device Name Characteristic |
| `Unknown Service` | 调试工具没有该自定义 UUID 的名称映射，不代表服务无效 |

## 6. 总结

BLE 可以沿着两条主线理解：GAP 解决“设备如何被发现并建立连接”，GATT 解决“连接后数据如何组织与访问”。分清 GAP 角色、GATT 角色以及 Service、Characteristic 和 UUID 的关系，就建立了继续学习 BLE 开发所需的基本框架。
